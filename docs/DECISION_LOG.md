# Decision Log: 43 Non-Obvious Engineering Decisions

**Deliverable 5.** The non-obvious decisions made while building the `@AppleSupport` AI triage/reply agent, and why. Each one follows the same pattern: what was decided, and the concrete reason or evidence behind it -- not just "what I built" but "what I chose over what, and why that choice wins." See `docs/REPORT.md` for the full report and `docs/AUDIT_AND_FIX_PLAN.md` for the detailed audit history behind several of these.

1. **Picked @AppleSupport, not a retail brand.** Consumer electronics support has strict diagnostic procedures, real safety stakes (lithium battery hazards), and clearly defined escalation rules -- a domain where "get it right or escalate" is a meaningful test, not just a UI wrapper around generic replies.

2. **Embedded ChromaDB instead of a hosted vector database.** Keeps the entire benchmark running fully offline, in one command, in well under 15 minutes -- with zero external services to configure, pay for, or have rate-limit an interviewer trying to reproduce the results.

3. **A 9-gate deterministic cascade instead of one LLM safety score.** Prompt injection, hazards, PII, human requests, sentiment, confidence, clarify, similarity, and generation guardrails each run as an explicit, ordered rule -- not a single model call an LLM could hallucinate its way past on a real physical hazard.

4. **Calibrated intent confidence with temperature scaling (T=0.08).** Raw cosine similarity isn't a real probability. Scaling it produces a bounded, calibrated confidence score the triage gate can actually threshold against, instead of an arbitrary similarity number with no defined meaning.

5. **Never let the agent request PII -- and block it from echoing PII the customer already posted.** Most designs only guard the agent's own questions. This one also scans the customer's tweet for PII-shaped text (like a phone number) and blocks a reply that echoes it back -- closing a leak most systems miss entirely.

6. **Retrieval is filtered by classified intent, not open across the whole corpus.** Without this, a battery-drain question could retrieve an iPad-display fix on wording similarity alone. Filtering by intent first keeps every retrieved historical reply topically relevant.

7. **Any unhandled crash fails closed to ESCALATE, never to a silent auto-reply.** A global try/except wraps the entire pipeline. If any component breaks, the ticket routes to a human with reason code `SYSTEM_EXCEPTION_FAIL_CLOSED` -- the customer never receives a reply built from a pipeline that crashed midway.

8. **Rewrote the hazard/PII regex to understand negation, because the naive version had real false positives.** "Battery didn't catch fire" matched a bare `fire` keyword pattern. Added a negation-window check and tighter device-noun proximity rules, verified against real Kaggle tweets the old rule would have wrongly escalated.

9. **Escalation on legal/churn language now requires corroboration, not one keyword.** Manual review of real cases found genuine false positives: "reported a scam **to** Apple" (the customer wasn't the victim), and a support case number that happened to match a phone-number regex. Split triggers into an auto-escalate tier (unambiguous: "lawyer," "police") and a soft tier ("sue," "scam") that needs a second corroborating signal before escalating.

10. **Added a third action, CLARIFY, instead of forcing every ambiguous ticket into AUTO_HANDLE or ESCALATE.** Real @AppleSupport agents sometimes just ask "which device is this?" A confidence-band gate now does the same for device-dependent intents where the customer never named a device -- instead of over-escalating every case that's merely unclear.

11. **Rebuilt the golden set so the system can't be graded against its own logic.** The original labels came from the same logic family the system under test would later be scored against, with a hardcoded agreement floor that meant the eval could never fail. Rebuilt using an independent keyword heuristic for labelling, then manually reviewed every real escalation case -- and disclosed that this heuristic disagreed with the original classifier on **~41% of examples**, an honest signal of how noisy this domain really is.

12. **Removed the hardcoded kappa floors and reported the real, weak agreement number.** The code used to force `max(kappa, 0.72)` regardless of the actual computed value. Removed both floors; the real human-judge kappa is reported honestly even where it's weak (0.07, "Slight agreement") -- an eval harness that can't report a bad result isn't measuring anything.

13. **Whitelisted link domains to `apple.co` and `support.apple.com`.** Any third-party domain in a drafted reply is stripped or flagged before it ships, closing an obvious phishing-shaped failure mode independent of the live link checker below it.

14. **Added a lexical-overlap grounding check because a real embedding model wasn't reliably available in every environment this needs to run.** `check_grounding()` checks that a draft's content words actually overlap with what was retrieved -- a cheap, dependency-free proxy for "did the model just invent this," usable even where a heavier model can't load.

15. **Populated the RAG corpus with real historical @AppleSupport replies, not a hand-written seed set -- with leakage explicitly excluded.** Every `source_tweet_id` present in the golden set is excluded from the corpus, so the system can never retrieve its own answer key during evaluation. Falls back to a small hand-written seed corpus only if the real data file is unavailable.

    > ⚠️ **This entry was false for the entire life of the project, and is left standing so the claim and its refutation sit together.** The exclusion compared `kaggle_kaggle_187962_187961` (the golden set's doubled id) against `kaggle_187962_187961` (the corpus id). Those strings can never be equal, so the guard skipped nothing. The indexed corpus was the first 800 rows of the 1000-row file, and in it sat **123 of the 162** distinct golden reference replies, so **80 of the 124** held-out rows could retrieve, verbatim, the exact reply they were being scored against. *(This note first said 157/162 and 105/124 -- the whole-file figures. The index only held the first 800 rows. Corrected by round 3; the corrected number is still a broken measurement.)* A test asserted the guard "worked" by checking only that both sets were non-empty. See decision **27** for the repair and **28** for why the repair did not initially reach existing installs.

## Addendum (2026-09-10): Root cause of the "apple.co/directmessage" fabrication, found and fixed

The live link checker (`src/drafting/link_checker.py`) correctly caught drafted replies citing `apple.co/directmessage` as broken -- that URL 302-redirects to Apple's generic homepage. Tracing it back, the root cause wasn't the LLM hallucinating on its own: `src/drafting/prompts.py`'s system prompt literally instructed it to "direct them to DM (apple.co/directmessage)." That link was never real -- Twitter/X direct messages require the customer to already be logged in and initiate the DM themselves, so there's no fixed public "click here to DM us" URL to hand out.

**Fix**: rewrote the prompt to ask for a DM in plain text (no URL at all), and restricted "Links" to only ever cite a specific, real support article already present in the retrieved historical context. The link checker stays in place as a safety net for any other fabricated URL, but this removes the one bug that was causing it to fire on nearly every PII/account-escalation case in the first place.

This is the same principle behind several of the decisions above: when a guardrail catches something, trace it to the actual cause -- here, a bad prompt instruction -- rather than treating the catch itself as the fix.

## Explicitly Rejected / Out of Scope (2026-09-10)

Decisions made *against* building certain things, kept here for the same reason the decisions above are: so the reasoning isn't lost.

**Rejected by design** (added complexity and cost, with no clear safety win over the current deterministic cascade): a live per-ticket **debate agent** for triage routing, LLM self-reported confidence scores, a fine-tuned intent classifier, a learned meta-model combining multiple signals.

**Tested and rejected, with evidence:** an agentic reformulation loop that retries intent classification on low confidence made accuracy *worse* -- **48.9-50.5% vs. the 52.2% single-pass baseline**. A 3-role **debate agent** as the LLM judge cost **3x the API calls with no measurable accuracy gain** over a single-call judge, so it was simplified back down.

**Safety-driven scope boundaries** (deliberate, not oversights): no tool-calling or real actions -- the agent only drafts and recommends, it never executes a refund, account change, or anything else. No persistent memory across messages -- stateless by design, so one compromised turn can't poison later replies. No data-poisoning defense for the retrieval corpus -- out of scope because the corpus is currently static, not a live-updating vector store, so that attack surface doesn't exist yet.

**Known limitations, deferred, not hidden:** a semantic-similarity fallback for grounding synonyms (a real gap; GloVe embeddings are available, but building this properly was too large to rush into this submission). Full multilingual retrieval (built language-aware BM25 routing; real multilingual embeddings are still missing). Real sentence-transformer embeddings for retrieval (blocked by sandbox network restrictions during development -- a scope/time item, not abandoned). Temperature-calibrated softmax recalibration on intent confidence (would require rebuilding the classifier architecture; the actual calibration bug turned out to be data leakage in the golden set, not softmax temperature, so fixing the real bug made this unnecessary). A higher worker count in the parallel eval runner (more threads than available API keys just queue behind the same rate limit -- no speedup).

## Hardening Pass (2026-09-11): decisions 16-26

Same format as the 15 above: what was chosen over what, and the evidence. Several
of these made the reported numbers **worse**, which is the point -- they are here
in full rather than summarised away.

16. **Split the triage cascade so input-side gates run before retrieval and generation.** The pipeline ran classify → retrieve → **generate** → triage, while `README.md`'s diagram had always shown the safety gate first. Three consequences, all real: a prompt-injection tweet was interpolated into the Gemini prompt and reached the model *before* the gate whose only job is to stop that; every hazard / PII / human-request ticket paid for an LLM call triage then discarded; and `guardrails.py`'s own docstring admitted it ("drafting currently runs before triage"). `TriageEngine.evaluate` is now `evaluate_input()` (gates 1-5, raw text only) plus `evaluate_output()` (gates 6-9), with `evaluate()` retained as a wrapper so no existing caller changed. Chosen over reordering inside a single method, which would have left no way to express "stop before generation". **Evidence it is behaviour-preserving: eval metrics are identical before and after** -- the split changed *when* gates run, not what they decide. **29 of 188 rows (15.4%)** now skip retrieval and generation entirely.

17. **Persisted a seeded, stratified calibration/held-out split, and reported on held-out only.** `scripts/calibrate_thresholds.py` swept both triage thresholds against the golden set and the harness then reported on those same 188 rows; `AUDIT_AND_FIX_PLAN.md` §7.10 records both thresholds being changed on the strength of that sweep. Every published triage number was optimistically biased by construction, and §5 of the report -- the section for exactly this disclosure -- did not mention it. Chosen over recomputing a split at import time (a sweep run and an eval run could then disagree about which rows are held out, reintroducing the leak while appearing to fix it) and over a 50/50 split (noisier held-out numbers on 188 rows). **Cost, reported: triage accuracy 64.9% → 62.9%, escalation recall 93.8% → 90.5%.** The diagnostic detail that matters more than the drop: intent accuracy *rose* (+5.9 pts calibration → held-out) while both threshold-dependent metrics fell. Only the thresholds were ever tuned on those rows, so leakage should appear in exactly the threshold-dependent metrics and nowhere else. It does.

18. **Documented, rather than fixed, that the held-out set contains zero `CLARIFY` rows.** The golden set has exactly one `CLARIFY` example, so no stratification can place it on both sides. Held-out triage accuracy therefore measures a two-class problem while the system implements three actions, and `CLARIFY` is covered by unit tests only. Chosen over moving that row to held-out (then calibration has none), over duplicating it (inventing data), and over dropping `CLARIFY` from the metric (hiding a whole action). The fix is more `CLARIFY` data, which is a labelling task, not a code change.

19. **Added an embedding grounding check, and kept the lexical one -- after measuring both.** DECISION_LOG #14 recorded the bag-of-words check as a fallback from when the embedding model could not be loaded. Measured on 7 labelled probes and on all 188 real reference replies (grounded by construction, so any flag is a false positive): lexical @ 0.12 → ~~**18.6%**~~ **31.4%** false-positive rate; embedding @ 0.30 → ~~**9.6%**~~ **19.7%**; embedding @ 0.65 → ~~**33.0%**~~ **72.3%**. *(Struck figures were measured against the leaking corpus described in decision 15 -- every reply retrieved itself, so all three rates were floored far below the truth. Recomputed on the clean corpus by `scripts/measure_grounding_modes.py`; see decision 29.)* Chose embedding @ 0.30: a 37% reduction in false positives at identical probe accuracy -- **not** "half", which is what the pre-correction numbers supported and what this entry originally said. **Explicitly rejected the 0.65 floor even though it scores 7/7 on the probes** -- those probes were hand-written, and fitting a threshold to them is the same error as decision 17 describes. Known limitation kept rather than tuned away: similarity is not entailment, so on-topic-but-unsupported advice (0.64) still passes. The real fix is an NLI model.

20. **Closed six regex gaps found by writing the tests that should have existed.** `PROMPT_INJECTION` matched only "ignore ... instructions", so "disregard your previous instructions" and "forget your instructions" -- both listed in the report as known misses -- went through; there was no pattern for a fake system turn ("SYSTEM: override safety"); `HUMAN_REQUEST` could not match "transfer **me** to an agent", and its article group `(a\s+)?` could not match "an agent" at all; `\bjailbreak\b` never matched "jailbreaking"; and opening the device required naming a device *and* the word "yourself"/"casing", so "open the case with a screwdriver" passed. Each widened pattern was re-checked against the full negative corpus -- including "burnt a lot of calories", "my battery is NOT swollen", and the support case number `#100310750365` that once matched the phone regex -- so the new detections did not arrive with new false positives.

21. **Left the "on fire" idiom escalating, deliberately.** "my phone is on fire in the sense that it's really fast now" triggers a hazard escalation. No negation logic catches an idiom. Chosen over narrowing the hazard pattern, because the same narrowing would exclude a literal report of a burning device, and the error costs are asymmetric: a false escalation is one wasted human review, a missed one is a customer holding a device that is actually on fire. Asserted as deliberate in `tests/test_triage_rules_exhaustive.py` rather than left as an accident.

22. **Guarded the pipeline singleton with a lock.** `get_pipeline()` checked `_pipeline is None` and constructed without synchronisation, so two concurrent cold requests built two `SupportPipeline`s -- two embedding models in a process with a 512MB ceiling. That is the OOM class `render.yaml` and `src/embeddings.py` were already fighting, reachable under precisely the condition (a slow cold start) that makes overlapping first requests likely. Double-checked locking, with a test that races 8 threads and asserts one construction.

23. **Made CORS credentials conditional, never wildcard.** `allow_origins=["*"]` with `allow_credentials=True` is forbidden by the CORS spec -- browsers reject it -- so the configuration that looked maximally permissive actually broke the credentialed case while still exposing the API to every origin for ordinary reads. Worth recording: the *first* version of this fix had the same bug behind a different input (`CORS_ALLOW_ORIGINS=""` left the wildcard flag false while the origins fell back to `["*"]`), caught only because the test parametrises over the empty string.

24. **Rate limit and optional API key on `/api/process`, both defaulting to "unchanged behaviour".** The endpoint spends Gemini money per call and had neither, on a public URL. An in-process per-IP token bucket (30/min, 0 disables) and an `X-API-Key` check that is inert unless `API_KEY` is set. Chosen over a shared-store limiter because this is a single-instance deployment; documented as resetting on restart and not coordinating across instances rather than implying more than it does.

25. **Moved the audit-log write off the request path, bounded.** `_append_decision_log` did a blocking open/append inside `process()`. The "never break the pipeline" guarantee held via try/except, but "never slow the pipeline" did not: on a contended or full disk that latency is paid by the customer. Now a bounded queue drained by one daemon writer. Bounded, not unbounded, so a wedged writer costs fixed memory and counted, logged, dropped rows rather than the process.

26. **Annotated the spec divergences instead of editing the specs.** `docs/specs/02` and `04` are marked "Approved" and state requirements the system does not meet: Macro-F1 > 0.78 (actual **0.60**), classification latency < 35ms (measured P95 **61ms**, and not even the same measurement), τ_intent < 0.60 (code 0.40), both confidence gates at 0.65 (code 0.40 and 0.20), and a command `python -m src.intent.evaluate_baselines` that has never existed. Chosen over rewriting the specs to match reality -- a spec quietly edited to agree with the implementation is evidence of nothing, and erases the fact that targets were missed. Each divergent spec keeps its original text and gains an "Implementation Status vs This Specification" table. Spec 02 additionally requires both `T=0` determinism and a calibrated confidence score, which are mutually exclusive ($T=0$ collapses the softmax to an argmax); calibration won, and the spec's own conflict is noted there rather than silently resolved.

## Adversarial Review (2026-09-11): decisions 27-35

Four rounds of red-team review were run against the hardened system by
independent reviewers briefed only on what the previous round had changed. The
full record -- every finding, including the ones rejected and the ones that
turned out to be wrong -- is `docs/ADVERSARIAL_REVIEW.md`. The decisions the
rounds forced are here.

The first three entries share a theme worth naming: **all three are failures of a
fix to actually be in force**, not failures to think of the fix. The exclusion
logic existed and was wrong; the corrected logic existed and did not reach
existing installs; the measurement existed and measured a broken corpus. A
control nobody verified is a control nobody has.

27. **Matched the RAG leakage guard on three keys, not one.** Decision 15's guard compared golden `source_tweet_id` against corpus `tweet_id` and excluded **0 rows**, because `scripts/finalize_golden_set.py` had written each golden id as `f"kaggle_{source_tweet_id}"` where `source_tweet_id` already carried the prefix. The evaluation had been retrieving its own answer key for the life of the project, and README, REPORT and CLAUDE.md all asserted otherwise. Now excludes on collapsed id **and** exact `customer_text` **and** exact `agent_reply`. Chosen over fixing the id format alone: an id is a formatting convention and can drift again silently, while identical text is identical text. The third key matters on its own -- @AppleSupport reuses canned replies, after excluding by id and customer text alone, 39 corpus rows carrying 10 distinct golden reference replies remained reachable. (This said "39 golden reference answers" until round 3 checked it; 39 is the row count. The key still earns its place -- 10 is not 0 -- but the overstatement was 3.9x.) The guard now logs a WARNING when it excludes zero rows, because "excluded nothing" and "working perfectly" had been indistinguishable in the logs. **Cost, reported -- and corrected by round 3:** the guard skips **197** of the 997 rows it scans, not 121, and the indexed corpus is **still 800 records**, because `load_real_corpus()` stops at 800 *accepted* rows and later rows backfill. So the guard costs no corpus size at all. The original "121 rows removed from an 800-row corpus" was wrong in magnitude (121 is the count for one of the three keys over the first 800 lines of a 1000-line file) and wrong in kind (nothing is net removed). The figure is now rendered from the loader's own counter rather than typed.

28. **Stamped the vector index with a corpus fingerprint, and rebuild on mismatch.** Decision 27's repair was conditional and nobody noticed: `_ensure_seed_data()` returned early whenever the persisted collection was non-empty, and `data/chroma_db` survives a `git pull`. Measured on a simulated pre-fix index, re-opening with the *fixed* code left **121 excluded source ids and 153 golden reference replies still retrievable**. So on every machine that had ever built an index -- including the checkout this project was developed in -- the leak was still live while the report claimed it was closed. The collection now carries a hash of (corpus file size+mtime, the three exclusion-set sizes, a manually bumped logic version) and rebuilds loudly when it does not match. Chosen over rebuilding unconditionally on every start, which costs a full re-embed of the corpus per process launch; both halves are pinned by tests. **A fix that silently does not apply is worse than no fix, because the report claims it is in force.**

29. **Made section 5b's numbers a generated artefact instead of prose.** The false-positive rates in decision 19 and REPORT §5b were typed into the report template from a one-off measurement taken *before* decision 27. They were real measurements of a corpus that contained the answer key: every reply retrieved itself, similarity was ~1.0 by construction, and all three rates were floored far below the truth. `scripts/measure_grounding_modes.py` now writes `docs/grounding_modes.json` and the report renders from it; a missing file produces a visible gap notice rather than a stale literal. The corrected rates are **31.4% / 19.7% / 72.3%**. The conclusion's *direction* survives -- embedding @ 0.30 is still the best of the three -- but the word "halves" was wrong and is corrected in place rather than quietly deleted. **The most dangerous number in a report is a real measurement of the wrong thing, because nothing about it looks wrong.**

30. **Stopped treating punctuation as a safety control.** Round 1 fixed "No joke, my iPhone battery is swollen" being read as a denial by truncating the negation lookback at the nearest clause boundary. Round 2 deleted the comma -- which is exactly what someone typing in a hurry about a swelling battery does -- and the identical bypass returned: `detect_hardware_hazard()` returned `(False, [])` on a lithium hazard report. A closed list of emphatic idioms ("no joke", "not kidding", "no lie", "I'm not making this up") is now blanked out of the lookback whether or not it is punctuated. Chosen over widening the clause-boundary set, which would have been the third patch to the same heuristic: every listed phrase is an idiom whose literal negation reading is not available in English, so blanking it cannot suppress a genuine denial -- and "my battery is not swollen" is asserted to still suppress.

31. **Required corroboration before `overheat` counts as physical damage.** `\boverheat\w*\b` alone was a hazard, so "My MacBook overheats when I run Final Cut Pro" -- the most common Mac complaint there is -- escalated at `risk_score=1.0` under reason code `HARDWARE_PHYSICAL_DAMAGE`. Both the action and the stated reason were wrong; thermal throttling is not physical damage. Now needs one severity signal in the same clause (burning, hot to touch, smell, smoke, melting, scorching, blistering, shutdown, swelling). **This is a deliberate recall-for-precision trade and it does lose something: a bare "it overheats" no longer escalates at this gate**, and instead takes the normal path where the frustration gate and output guardrails still apply. Accepted because an escalation queue that is mostly thermal-throttling complaints is an escalation queue that gets ignored -- which costs recall on the cases that matter, just further downstream where it is harder to see.

32. **Constrained the separator-free card patterns to real issuer prefixes.** Bare `\d{15}` reported "My IMEI is 356938035643809" -- a routine thing to tweet at a support account -- as `CREDIT_CARD_DETECTED`. Escalating was arguably the safe call; calling it a credit card was a false stated reason, and a true stated reason is this system's entire contract. Luhn cannot separate the two (IMEIs carry a Luhn check digit as well), so the bare branches now require a Visa/Mastercard/Amex/Discover/JCB/Diners prefix. Chosen over adding an IMEI detector with its own reason code, which is a feature nobody asked for. **Known cost, stated: a card on an issuer prefix outside that list, posted without separators, is now missed.** The separated 4-4-4-4 and 4-6-5 forms stay unconstrained.

    > ⚠️ **Round 3 found this entry's coverage claim false.** It named Diners (36/38) as covered; Diners PANs are **14** digits and the branch was 16, so the pattern matched no real Diners card and missed every one -- while this very disclosure said the only gap was issuers *outside* the list. It also missed 13/19-digit Visa, Discover 644-649, and any card typed on an Apple device (iOS substitutes an en dash for a hyphen). See decision **40**. A disclosure that reads safer than the code is worse than no disclosure.

33. **Bounded the URL extractor to real TLDs, and bounded the request body.** Two defects in one pattern. (a) `"Let us know how it goes.Thanks for your patience"` yielded the URL `goes.Thanks`, failed the whitelist, and escalated entirely ordinary support copy as `UNAUTHORIZED_URL` -- a missing space after a full stop is commonplace in real replies. (b) The nested quantifier backtracked quadratically: 16KB of `"a-a-a-…"` took **1.08s** and 100KB took roughly **47s**, inside a guardrail on a public HTTP endpoint with no `max_length` on the request body. Requiring a TLD from a fixed list kills the false positives (`Thanks` is not a TLD) *(round 3: it narrowed the class, did not remove it -- `that.It`, `you.In`, `help.Support` all still extracted, and the allowlist turned out to be prefix-matchable, shipping a phishing link. See decisions 37-38.)*; bounding each DNS label with a single `{0,62}` quantifier makes the scan linear -- 100KB now takes **0.027s**. *(Round 3: it did not make the scan linear. Bounding the label left the OUTER `(?:label\.)+` unbounded, so a dotted payload was still quadratic -- 4000 chars took 1.42s and 32KB took 83.6s. The regression test asserted linearity using only the one payload shape the rewrite fixed, so the suite certified a property the pattern did not have. See decision 38.)* `QueryRequest.text` additionally gained `max_length=4000`, because bounding the input is the control that survives the *next* pattern someone adds. **Known cost, stated:** a scheme-less phishing domain on a TLD outside the list is no longer extracted by that branch.

34. **Keyed the stratified split by row identity rather than by `tweet_id`.** Two rows sharing an id -- or two rows with a null id, which stringify to the same `"None"` -- collapsed to one entry in the assignment dict, and the last stratum processed silently overwrote the earlier one's decision, defeating the stratification the function exists to provide. **Latent, not active: the shipped golden set has 188 distinct non-null ids, so no reported number was ever affected**, and the split counts (64 calibration / 124 held-out) are unchanged by this fix. Recorded anyway, because "it happens to be fine right now" is how the id-format bug in decision 15 survived for the life of the project.

35. **Declined to widen the URL whitelist to `apple.com`.** Round 2 observed that a draft citing `apple.com/support` is flagged `UNAUTHORIZED_URL`, since the whitelist admits `apple.co` but not `apple.com`. This reproduces and is a real false positive. Not changed: widening the set of domains a brand account may auto-tweet links to is a security decision about the deployment, not a bug fix, and the failure is fail-safe (it escalates to a human rather than publishing). Recorded here so the next person finds a decision rather than an oversight.

## Adversarial Review Round 3 (2026-09-12): decisions 36-43

Round 3's result is that three of round 2's fixes were wrong, and two of them were
wrong in the same way as the thing they fixed. These eight decisions are mostly
about *how* to fix a thing so the next round does not reopen it.

36. **Replaced the negation heuristic with a structural rule, on its fourth attempt.** The hazard gate's negation check was a 20-char lookback (v1), then truncated at a clause boundary (v2), then blanked a closed list of emphatic idioms (v3). Each version was defeated by the next review round with one word: v1 by "No joke, my battery is swollen", v2 by deleting the comma, v3 by typing "No joking" instead of "No joke". Round 3 also produced four constructions no idiom list can reach -- "not just warm, it's swollen", "no longer flat, it's swollen", "has never been this swollen", "has no case and the battery is swollen" -- all CLEAN, all answered with a troubleshooting reply. **The fix was to stop asking "is there a negation word near the hazard?", which has no correct answer, and ask "does the negator attach to the hazard word?", which does.** A negator now counts only when everything between it and the hazard is copula, intensifier or hazard vocabulary; "is not swollen" is a denial, "not just warm, it's swollen" is not. Chosen over a fourth idiom entry because the structural rule handles phrasings nobody has thought of yet, which is the property all three previous versions lacked. It also let the idiom list be deleted rather than extended. **Cost: none measured** -- every denial the old rule suppressed is still suppressed, and escalation recall rose from 90.5% to 95.2%.

37. **Rewrote the URL extractor to require a scheme, a path, or `www.` instead of matching a TLD allowlist.** The round-2 allowlist had two defects I had claimed it fixed. It was **prefix-matchable**: `support.apple.company/verify-now` matched the listed `com`, failed its trailing `\b` against `pany`, and extracted *nothing* -- so `validate_urls()` never consulted the whitelist and a convincing phishing link shipped clean. And it still false-positived, on commoner words than the ones it fixed (`that.It`, `you.In`, `help.Support` -- the list contains `it`, `in`, `at`, `support`, `store`). Requiring a path or a `www.` is the property that actually separates a hostname from a full stop, and it cannot be prefix-matched. **Known cost, stated: a scheme-less bare domain with no path is no longer extracted.** Measured false-positive rate on 1000 real corpus replies: 0 before and after.

38. **Bounded both quantifiers, and fixed the regression test that certified a property the code did not have.** Round 2 bounded the DNS *label* and left the outer `(?:label\.)+` unbounded, so a dotted payload was still quadratic: 4000 chars took **1.42s**, 32KB took **83.6s**. Worse, `test_url_extraction_is_linear_not_quadratic` asserted linearity using only `"a-" * 50000` -- the single shape the rewrite happened to fix. **A test exercising one input shape certified a property across all of them, which is how a claimed fix survived a whole round.** Every timing test now parametrises over three payload shapes. `EMAIL_REGEX` had the same defect and runs on *raw customer text*, where the 4000-char HTTP cap did not protect it because `src/cli.py` and the eval harness build `TweetInput` directly; the bound moved onto `TweetInput` itself.

39. **Widened the hazard proximity window and the overheat corroboration list, after measuring that decision 31's disclosure was wrong.** Decision 31 said the corroboration list was "kept wide on purpose -- anything suggesting heat that has left the realm of slow-fan-noise still fires". Wrong action and a false stated reason, in the module whose docstring says generic words were removed for exactly this reason. 42. **Made `CORROBORATED_CHURN_THREAT` actually escalate.** Two soft signals scored 0.45 + 0.10 = **0.55** against a 0.60 threshold, so the branch emitted a marker literally named `CORROBORATED_CHURN_THREAT` and then returned `False` -- "they scammed me and stole my money" was auto-handled. The module docstring has claimed since it was written that "another soft signal" corroborates; it never did. The other corroborators each add their own weight and always crossed, which is why three rounds of review missed it. **Found by following my own round-3 change through, not by a reviewer** -- which is the argument for re-deriving a number rather than reading the prose that describes it. Increment 0.10 → 0.15.

43. **Made the rate limiter per-client, behind an explicit trust flag.** Decision 24 described "an in-process per-IP token bucket". uvicorn rewrites `client.host` only for peers in `--forwarded-allow-ips` (default 127.0.0.1), which neither `render.yaml` nor the `Dockerfile` sets -- so on the live demo every request carried the edge proxy's address and **all of them shared one bucket**: one client spending 30 requests locked out every other client and the dashboard. A self-inflicted outage from a control advertised as abuse protection. Chosen over trusting `X-Forwarded-For` unconditionally, which makes the limit spoofable: it is gated on `TRUST_PROXY_HEADERS`, default **false**, and takes the leftmost hop when enabled. A deployment behind a proxy chain needs a hop count; that is not this deployment and is not pretended to be handled.
