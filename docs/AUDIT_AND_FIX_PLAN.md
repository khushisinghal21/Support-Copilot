# Audit: Method Used, Gaps Found, and a Fix Plan

This is an honest read of what `hiver_assignment` actually does today, as opposed to what the README and REPORT claim it does. It's written assuming you'll be asked to explain and modify this code live, so it prioritizes the things that would embarrass you in that room over cosmetic issues.

> **Update**: Sections 1-6 below are the original audit, left unedited as a record of what was found. Section 7, added afterward, tracks what was actually fixed following that audit and your explicit request to reduce false positives, remove static/fabricated numbers, and add safety guardrails. Read Section 7 first if you want the current state; read Sections 1-6 for the original reasoning behind each fix.

## 1. The method, as actually implemented

The pipeline is a four-stage system for `@AppleSupport`. A tweet goes through `SemanticCentroidClassifier` (`src/intent/classifier.py`), which embeds the text with `all-MiniLM-L6-v2` and compares it by cosine similarity to five class centroids. Each centroid is the mean embedding of 8 hand-written example sentences per class, defined in `src/intent/taxonomy.py` — there is no training on labelled data anywhere in this classifier; it's a zero-shot nearest-centroid model. Below a confidence threshold it falls back to `OUT_OF_SCOPE_AMBIGUOUS`.

The result feeds `HistoricalRetriever` (`src/drafting/retriever.py`), which does an intent-filtered nearest-neighbor search in a local ChromaDB collection. That collection is seeded once from `src/drafting/historical_data.py`, a hand-written list of about 40 customer/agent pairs — it is not the 300+ real `@AppleSupport` pairs your team already extracted from Kaggle into `data/apple_support_kaggle_pairs.jsonl`. That extraction script (`src/data/ingest_kaggle.py`) exists and clearly ran once (the JSONL file is full of real, messy tweets), but nothing in the live pipeline ever loads it into Chroma. The "grounded in real historical brand data" claim in the README is true of a file sitting unused on disk, not of what the running system actually retrieves from.

`GroundedReplyGenerator` then either calls Gemini (if `GEMINI_API_KEY` is set) with the retrieved snippets as context, or — with no key, which is the default — just returns the single nearest retrieved snippet verbatim, or a hardcoded generic line if nothing was retrieved. So "RAG generation" in the reproducible-in-15-minutes path is nearest-neighbor copy-paste, not generation. That's a defensible baseline in its own right, but it's not what the README describes.

`TriageEngine` (`src/triage/engine.py`) is a cascade of deterministic gates checked in this order: hardware/thermal hazard regex, PII regex, "talk to a human" regex, a keyword-based frustration/legal-threat score, low intent confidence, low retrieval similarity, and failed output guardrails. Anything that clears all of them is `AUTO_HANDLE`; anything else is `ESCALATE` with a reason code. This part is genuinely sound as an architecture — fail-closed, explainable, no LLM in the safety-critical path.

The evaluation harness (`src/eval/runner.py`) loads `data/golden_eval_set.jsonl`, runs a trivial majority-class baseline, a TF-IDF+LogisticRegression baseline, and the production pipeline over it, computes Macro-F1/accuracy/ROUGE-L/escalation-recall, grades 50 replies with `LLMJudge`, and computes Cohen's kappa against `data/human_annotations_sample.jsonl` to argue the judge is calibrated. All of this machinery is real and reasonably well-built. The problem is what it's being run on.

## 2. The critical gap: the golden set and the human calibration are fabricated, not collected

This is the one to fix before anyone else reads this repo.

`src/eval/curate_datasets.py::build_golden_dataset()` does not sample anything from Twitter. It defines 15–40 hand-written example sentences per intent class directly in Python (as tuples with the label already attached), then mechanically loops over them 4–5 times, prepending strings like `"Hey @AppleSupport, "` or appending `"(case #123)"` to manufacture 200 rows from ~40 originals. `data/README.md` describes this as "Stratified Purposive Sampling from the Kaggle... dataset" with a four-step labelling protocol — that description does not match what the code does. There is no sampling step anywhere; the dataset never touches a real tweet. The assignment is explicit that the golden set must be examples "you built yourself" by sampling and labelling real data — this doesn't satisfy that, and it's easy to notice by opening the file.

It gets worse with the human calibration set. `build_human_annotations()` assigns "human" scores with rules like `groundedness = 5` unless `i % 7 == 0`, or based on whether the text contains an edge-case tag — there was no human annotator. Then `src/eval/human_agreement.py::compute_human_judge_agreement()` computes a real Cohen's kappa from this synthetic data, and then overrides it: `effective_kappa = round(float(max(kappa_g, 0.72)), 4) if exact_g >= 0.75 else round(kappa_g, 4)`. Whatever the actual kappa comes out to, if exact agreement is high enough the number is floored at 0.72 and reported as "Substantial Agreement." The kappa for safety is similarly floored at 0.70. This means the headline "κ = 0.72, human-validated" claim in the README badge is not a measurement — it's a constant with a measurement-shaped wrapper around it.

The top-5 failure analysis has the same problem one level up: `runner.py` computes a real `failures` list by comparing predictions to ground truth, and then never uses it. The "Top 5 Failure Modes" in REPORT.md — including the specific frequencies like "~35% of error cases" — is a separate hardcoded list (`top_5_failure_analysis`) written directly in the runner, disconnected from whatever the pipeline actually got wrong on that run. The failure modes described are plausible and well-written, but they are not derived from evidence the repo can produce.

None of this means the underlying system is bad — the architecture is reasonable. It means the proof is currently theater. Given that Hiver says explicitly "the proof is worth more than the system" and that they'll ask you to explain your own code live, this is the single highest-priority thing to fix, and it's very fixable: you already have real data sitting in `apple_support_kaggle_pairs.jsonl` to build a real golden set from.

## 3. Leakage that inflates every number, even if the fabrication weren't there

Compare `historical_data.py`'s seed pair `"My iPhone 11 keeps freezing and won't respond to touch after the update."` to `golden_eval_set.jsonl`'s `"My iPhone 11 keeps freezing and won't respond to touch after iOS 11 update."` — these are near-duplicates. That's not a coincidence: the golden set, the RAG seed corpus, and the intent-centroid prototypes all appear to have been written from the same small pool of example sentences by the same author in the same session. `SimpleTfidfClassifier` (Baseline 2) is fit only on the 40 `INTENT_PROTOTYPES` sentences (`_fit_default_corpus`), which are drawn from the same pool the golden set paraphrases. So both baselines and the production classifier are being tested on near-duplicates of what they were built from — the reported 80–87% accuracies mostly reflect string memorization, not generalization to real, messy tweets. This is a second, independent reason the headline numbers won't survive scrutiny even after you remove the hardcoded kappa floor.

## 4. Other real gaps, roughly in order of how much they matter

The triage keyword lists are brittle in ways that are easy to demonstrate live. `ANGER_KEYWORDS` in `src/triage/sentiment.py` includes ordinary words like "trash", "garbage", and "useless" with no negation handling, so "this update isn't garbage, it actually fixed things" would still score as anger. `PHYSICAL_DAMAGE_REGEX` in `src/triage/rules.py` matches the bare phrase "hardware issue" or "hardware failure", which would force-escalate an ordinary "I think this is a hardware issue with my keyboard shortcuts" query that has nothing to do with safety. `PHONE_REGEX` only matches US-format numbers. None of these rules understand negation ("my battery is NOT swollen"), so the system's one real safety strength — zero missed escalations — is currently being measured against test cases written with the same vocabulary as the regexes that catch them, which is circular.

There's a real discrepancy between what the docs claim and what the code does on thresholds. The README says the confidence guard fires below `τ = 0.60`; `config.py` actually sets `MIN_INTENT_CONFIDENCE = 0.35`. `src/triage/reasons.py` hardcodes the string `"tau < 0.65"` into the escalation explanation shown to the customer/reviewer regardless of what threshold was actually configured or used — so the stated reason for a decision can misdescribe the decision.

The ROUGE-L grounding score for the production system (0.2862) is lower than for the naive Baseline 2 (0.3628), because Baseline 2 always emits the same boilerplate sentence pointing to apple.co, which happens to have more lexical overlap with the templated reference replies than the system's actual retrieved answers do. The README renders this as `"+-0.0766"` — a sign error that hides a real regression instead of explaining it. This is exactly the kind of thing the "What's misleading about my headline number" section is supposed to surface, and currently doesn't.

The LLM judge and the reply generator both fall back to keyword heuristics when no API key is present (`if "apple.co/" in reply: groundedness = 5`), which is also the guardrail's own success criterion — so in the no-API-key path, the judge is partly grading the system on whether it did the thing the judge is looking for, not on independent quality. If you're running this benchmark without a live LLM key, the "LLM Judge Quality: 4.7/5" label is inaccurate; it should say "heuristic judge," and you should either budget for a handful of real API calls or be upfront that the judge numbers are the deterministic fallback, not an LLM.

The system is single-turn only, evaluating and replying to one tweet in isolation, even though this Twitter support dataset is heavily multi-turn by nature (customers clarify device type, agents ask follow-ups). The report already names this as a limitation, which is good, but it means the "grounded reply" claim is grounded in a version of the problem that's narrower than what real `@AppleSupport` traffic looks like.

Smaller things worth a pass: the missed-escalation denominator is hardcoded as `/ 30` in both the terminal table and the generated report regardless of how many true escalations are actually in whatever golden set is loaded, so it will silently show the wrong denominator once the golden set changes; and `data/README.md`'s schema example uses field names (`ground_truth_intent`, `stated_reason`, `is_adversarial`) that don't match the real file's actual field names (`true_intent`, `expected_stated_reason`, `is_edge_case`), which is a small thing but the kind of inconsistency that erodes trust once someone starts cross-checking.

## 5. How to fix it, in priority order

**Before anything else:** rebuild `data/golden_eval_set.jsonl` from real data instead of templates. You already have the raw material in `apple_support_kaggle_pairs.jsonl` — sample roughly 200 rows from it (stratify across the five intents using the `intent` field it already carries, plus a manual pass to pull in genuine safety/PII/frustration edge cases from the full corpus, since those are rare and stratified sampling alone won't surface enough of them), then hand-label `true_intent`, `true_triage_action`, `expected_stated_reason`, and write a short `reference_resolution` yourself for each — you can use an LLM to draft first-pass labels to save time, but you have to review every one and the write-up needs to say so plainly, since "AI-assisted, human-reviewed" is a fine and expected answer to "how did you label this" and "a script generated it and called it hand-labelled" is not. Once this is real, rerun everything — expect the accuracy and escalation-recall numbers to drop, possibly a lot, and that's fine; a defensible 70% beats an indefensible 87%.

**Immediately after:** get a real second opinion on 50 of the held-out replies for the human-agreement check — ideally an actual other person, or you doing a blind second pass on a different day — and delete the `max(kappa_g, 0.72)` floor in `human_agreement.py` entirely so the report shows whatever kappa actually comes out. If it's mediocre (say κ=0.3–0.5), say so and explain why in the "misleading" section — that's a more credible deliverable than a suspiciously round 0.72. Same principle for the top-5 failure list: delete the hardcoded `top_5_failure_analysis` in `runner.py` and instead cluster the `failures` list that's already being computed there but discarded, so the failure modes and their frequencies come from an actual run.

**Then close the RAG gap:** index `apple_support_kaggle_pairs.jsonl` into ChromaDB (the `ingest_kaggle.py extract` command already does this, it's just never wired into the default startup path) either as the primary corpus or alongside the hand-written seed set, and check for near-duplicate overlap between whatever ends up in the golden set and whatever ends up in the RAG/prototype corpora so you're not testing retrieval against its own training examples. Also decide, and state explicitly, what happens when `GEMINI_API_KEY` isn't set: don't call the fallback path's output "LLM Judge Quality" or "grounded generation" in the report — name the fallback for what it is, and if possible spend the (cheap) API budget to get at least the headline numbers from a real Gemini call.

**Cheap fixes that remove easy "gotcha" questions:** align `MIN_INTENT_CONFIDENCE` between `config.py` (0.35) and the README's stated 0.60 — pick the one you actually validated and update the other; stop hardcoding `"tau < 0.65"` in `reasons.py` and interpolate the real configured threshold; fix the `/ 30` denominators to use the real count of true escalations in whatever golden set is loaded; fix the ROUGE-L sign/formatting bug in the README table and add one sentence explaining why boilerplate baselines can out-score grounded replies on lexical-overlap metrics; and reconcile `data/README.md`'s example schema with the real field names in the JSONL.

**Worth doing if time allows, lower priority than the above:** add basic negation handling to the triage regexes (a simple "not|isn't|never" lookbehind before the hazard/anger keyword would kill the most obvious false positives), trim `ANGER_KEYWORDS` of overly generic words like "trash"/"garbage"/"useless", and extend the PII phone regex beyond US formats. These make the safety story more credible without being a large engineering lift.

**Genuinely one-more-week items**, already correctly identified in your own report and worth keeping as stated: multi-turn thread context via `in_reply_to_tweet_id`, active-learning feedback from human accept/reject/edit decisions, and automated red-teaming against prompt injection / fake-policy generation.

### 7.10 Threshold calibration: the real numbers, and why the "statistically optimal" answer was rejected

Once you ran `python -m src.eval.runner` successfully in your own terminal (Section 7 above predicted this would work outside the audit sandbox, and it did), the headline numbers exposed a real regression the sandboxed session couldn't have caught without the embedding model: **Triage Accuracy dropped to 43.1%, below both baselines**, even though Escalation Recall rose to 96.9% (missing only 1 of 32 true escalations, down from 24-32 missed before this pass). The system was massively over-escalating: roughly two-thirds of true-AUTO_HANDLE queries were being force-escalated.

Running `scripts/calibrate_thresholds.py` (written in the audit session but unexecutable there, now run for real) isolated the cause precisely:

```
=== MIN_INTENT_CONFIDENCE sweep (tau=0.35 current) ===
  0.35 |  12/72 wrong preds caught (16.7%) | 5/116 correct preds needlessly escalated (4.3%)

=== MIN_RETRIEVAL_SIMILARITY sweep (tau=0.40 current) ===
  0.40 |  15/33 true-escalate rows below tau (45.5%) | 94/155 true-auto-handle rows below tau (60.6%)
```

`MIN_RETRIEVAL_SIMILARITY = 0.40` was the dominant cause: **60.6% of legitimate AUTO_HANDLE queries** had a real-corpus retrieval similarity below that bar and were getting force-escalated by Gate 7 alone. The likely mechanism: `0.40` was implicitly tuned back when the RAG store was seeded from a ~40-example hand-written corpus that nearly duplicated the golden set (the leakage bug from Section 3) — similarity scores in that world were artificially high. Once the real, diverse Kaggle corpus was wired in (Section 7.6) to fix that leakage, genuine cosine similarity between a random real tweet and its nearest real historical neighbor is naturally much lower, and the threshold was never re-tuned alongside that architectural change. This is a good illustration of why a threshold needs to be re-validated any time the thing it's measuring changes upstream, not just set once.

**The tempting-but-wrong fix**: the script's own Youden's-J-optimal suggestion for `MIN_RETRIEVAL_SIMILARITY` was `0.50` — *raising* it further. Applying that blindly would have made things worse: at 0.50 the false-escalation rate climbs to 77.4% (up from 60.6%), for only 15 more points of recall on true escalations that four *other* dedicated gates (hazard, PII, human-request, frustration) already catch before Gate 7 ever runs. The full curve shows Youden's J stays close to zero across almost the entire sweep (never exceeding ~7.4%), meaning retrieval similarity is a genuinely weak discriminator between escalate-worthy and routine queries — unsurprising in hindsight, since "do we have a reasonable historical answer to ground a reply in" (this gate's actual job, and the reason it exists in `src/drafting/guardrails.py`'s grounding check too) is a different question from "is this query dangerous or hostile" (the job of the gates ahead of it). Treating it as a primary safety signal was a design assumption baked into the original architecture that the real data didn't support once measured.

**What was changed instead** (`src/config.py`): `MIN_RETRIEVAL_SIMILARITY` lowered from `0.40` to `0.20` (drops this gate's false-escalation rate on true-AUTO_HANDLE rows to 8.4%, at the cost of only 1 of 33 additional missed escalations that other gates were already catching most of anyway) and `MIN_INTENT_CONFIDENCE` raised modestly from `0.35` to `0.40` (catch rate 16.7% -> 26.4% for a false-escalation cost of only 4.3% -> 8.6% -- a much better trade than the confidence sweep's own Youden's-J pick of `0.55`, which costs 27.6% false escalations for a 68.1% catch rate).

**Still on you**: rerun `python -m src.eval.runner` with these new values and confirm Triage Accuracy actually recovers to a sensible level without meaningfully hurting Escalation Recall. If it doesn't fully recover, the next thing to check is whether `false_escalation` is still the dominant category in the regenerated report's "Top Failure Modes" section (Section 4) — if so, look at the specific example queries it surfaces rather than moving the threshold further, since a third mediocre threshold guess is not more defensible than the first two. This whole exercise -- measure, find the weak signal, reject the "optimal" answer for a reasoned one, document why -- is exactly the kind of decision worth being ready to explain live.

### 7.11 Following the failure-mode data: two real bugs found, not more threshold-tuning

After the 7.10 threshold fix, Triage Accuracy recovered from 43.1% to 58.0% -- real progress, but still well below both baselines (75-82.5%), and Escalation Recall barely moved (93.8% vs 96.9%), confirming the threshold fix wasn't the whole story. Rather than adjust thresholds a third time, the actual "Top Failure Modes" section from that run (mined from 112 real mismatches by `src/eval/failure_analysis.py`) was read directly, and it pointed at two specific, fixable bugs -- neither of them a threshold:

**Bug 1 (the bigger one, ~38% of all failures): `OUT_OF_SCOPE_AMBIGUOUS` prototypes conflated angry tone with no-content.** Real example: *"I just gotta say, you're support in the store is pathetic. My watch is stuck on UK time and NO ONE knew how to fix it. Really?"* -- a perfectly answerable HOW_TO_CONFIGURATION query, phrased angrily. It got classified `OUT_OF_SCOPE_AMBIGUOUS`, which `src/triage/engine.py`'s Gate 6 hard-escalates *unconditionally*, regardless of confidence. The root cause: two of the eight `OUT_OF_SCOPE_AMBIGUOUS` prototype sentences in `src/intent/taxonomy.py` -- *"Why does this always happen to me smh worst day ever"* and *"Apple is the absolute worst company in history lol"* -- are generic frustrated venting, not genuinely content-free/off-topic text. Any angry-but-legitimate complaint cosine-matches those just as well as an actual rant about nothing. This is the intent-classifier's version of the exact same bug class fixed in `src/triage/sentiment.py`'s `ANGER_KEYWORDS` during the original hardening pass (Section 7.4) -- tone was being used as a proxy for something it doesn't actually indicate. **Fix**: replaced those two prototypes with genuinely off-topic ones (a meme reference, an unrelated sports comment), keeping the six already-good content-free/off-topic examples (greetings, "order a pizza", small talk, testing-the-bot, unintelligible text).

**Bug 2 (~16% of all failures): `DEVICE_NOUN_REGEX` missed devices with an attached model number.** Real example: *"since the latest iOS update, my iphone6 is a lot choppier and slower. Anything I can do?"* -- named the device, but the CLARIFY gate fired anyway asking which device it was. Root cause: the regex `\b(iphone|ipad|...)\b` requires a word boundary immediately after the device name, but `\b` never fires between a letter and an attached digit (both are "word characters" to the regex engine) -- so "iphone6" never matched `\biphone\b` at all, only bare "iphone" did. Extremely common real-world phrasing (`iphone6`, `iphone11`, `ipad2`, `macbookpro`) was invisible to `mentions_device()`. **Fix**: changed the single-word device patterns to `\b(iphone|ipad|ipod|macbook|imac)[a-z0-9]*\b`, which absorbs any attached model suffix without needing to enumerate every model Apple has ever shipped. Verified directly (`mentions_device()` doesn't need the embedding model): `tests/test_hardening.py::test_mentions_device_handles_attached_model_numbers` and `test_clarify_does_not_fire_when_device_has_attached_model_number`.

Neither of these could have been found by staring at the code or by more threshold sweeping -- they only became visible once a real run's actual failures were mined and read individually, which is the whole point of replacing the hardcoded failure list with `mine_failure_modes()` in Section 7.7. The intent-classifier prototype fix could not be verified in this environment (no embedding model access) and needs a rerun to confirm; the regex fix was verified directly and is covered by the new tests. **Still on you**: rerun `python -m src.eval.runner` again and check whether Triage Accuracy and Intent Accuracy both improve, and whether `false_escalation` is still the top failure category in the regenerated report -- if a different pattern shows up, read that one too rather than guessing.
